# Project Research Summary

**Project:** Takoyaki — Octatrack Desktop Backup/Versioning/File Management
**Domain:** Desktop hardware sampler manager — binary file parsing, atomic filesystem operations, snapshot versioning
**Researched:** 2026-04-29
**Confidence:** HIGH

## Executive Summary

Takoyaki is a Tauri v2 desktop application that manages Elektron Octatrack project files mounted via USB. The tool's core value is data safety: no existing competitor (OctaEdit is dead, OctaStudio is unstable beta, OctaLib is Windows-only) provides backup, versioning, snapshot protection, or atomic write guarantees. The recommended approach builds on a strict three-layer safety model — auto-snapshot before every write, dry-run preview, and atomic staged writes via temp-file-then-rename — implemented in Rust with `binrw` for binary format parsing, `atomic-write-file` for write safety, and content-addressed snapshot storage backed by SQLite. The frontend is React 19 with Next.js in static/SPA export mode, communicating via Tauri IPC with typed bindings generated by `tauri-specta`.

The central technical risk is the OT binary format itself. The project file stores sample slot IDs one-indexed while every other file type (bank, markers, sample settings) uses zero-indexed IDs. Writing any of the up to 18 files affected by a single slot assignment with the wrong index convention silently corrupts the project. Unknown/reserved bytes must also be preserved verbatim on round-trip: 31.6% of the format is undocumented, and zeroing those bytes destroys forward compatibility. The binary parser must be treated as a safety-critical component: built first, isolated from Tauri, and validated with byte-exact round-trip tests against a corpus of real OT project files before any write path is built.

A second significant risk is legal: `ot-tools-io` is the most complete public OT format reference but is GPL v3. A clean-room specification document derived from independent community sources (Elektronauts threads, hex analysis, OctaLib research notes) must exist before any parser code is written. Additionally, staging files for atomic writes must occur on the CF card volume itself, not in `/tmp` — cross-filesystem renames are not atomic on macOS, and FAT32 write buffers require explicit `fsync` before the UI can report success. These constraints are non-negotiable and must be addressed in the foundation phase.

## Key Findings

### Recommended Stack

The stack is well-determined. Tauri v2 (2.10.3) is already decided; all library choices flow from it. `binrw` (0.15.1) is the correct parser for OT's fixed-layout binary structs — its derive macro approach maps exactly to OT's format, and it supports both read and write from a single annotation. `nom` (8.0.0) supplements binrw for any non-seekable or variable-length sub-sections. `rusqlite` (0.39.0) with the `bundled` feature handles Takoyaki's own SQLite and cross-attaches Wallflower's database read-only via standard SQLite `ATTACH DATABASE`. `zip` (8.6.0) is preferred over tar for snapshot archives because it has a central directory allowing random file access without full extraction. `tauri-specta` (2.0.0-rc.24) generates TypeScript types from Rust command signatures, eliminating IPC shape mismatches. `thiserror` covers command-boundary errors; `anyhow` covers internal propagation (never return `anyhow::Error` from a Tauri command — it does not implement `Serialize`). Both `notify` (9.0.0-rc.3) and `notify-debouncer-full` (0.8.0-rc.1) are RC-track; this is intentional — the 6.x stable line has poor macOS FSEvents handling. The `tauri-plugin-dialog` pattern (user picks CF card root via native folder picker, path stored in settings) is the correct approach for USB volume access — never hardcode `/Volumes/**` in capabilities.

**Core technologies:**
- Tauri 2.10.3: desktop shell, IPC, OS integration — the decided runtime; v2 is stable
- Rust stable (1.78+): backend — memory-safe binary parsing and atomic filesystem ops
- React 19 / Next.js 15 (static export): frontend UI — consistent with Wallflower; TanStack Query + Zustand
- `binrw` 0.15.1: OT binary format parsing — declarative derive-based struct layout; handles big-endian, magic bytes, alignment
- `nom` 8.0.0: supplemental parser combinators — for irregular or variable-length OT sub-sections
- `atomic-write-file` 0.3.0: write-then-rename per file — encapsulates POSIX atomic write pattern
- `zip` 8.6.0: snapshot archives — random file access without full extraction; universally accessible to musicians
- `rusqlite` 0.39.0 (bundled): application DB + Wallflower ATTACH — synchronous, no async overhead, bundled SQLite avoids macOS version variance
- `tauri-specta` 2.0.0-rc.24: TypeScript type generation from Rust — eliminates IPC shape bugs
- `notify` 9.0.0-rc.3 + `notify-debouncer-full` 0.8.0-rc.1: filesystem watching — active maintained line; use Kqueue backend, not FSEvents

### Expected Features

The competitive landscape is clear: no existing tool provides backup, versioning, or write safety. That is Takoyaki's primary differentiation vector. OctaStudio (beta) and Project Manager (active) cover the browsing/visualization baseline, which means Takoyaki must match those at launch and surpass them on safety.

**Must have (table stakes — v1 launch):**
- USB mount detection and connection status — entry point for all other features
- Project listing with metadata (name, bank count, tempo, last modified) — every competitor has this
- Bank and pattern visualization (populated/empty per bank/pattern) — OctaLib has it; users expect it
- Sample slot listing: Flex + Static, 128 each, with file paths — #1 user complaint about current tools
- Missing sample detection (broken references) — OctaStudio and Project Manager both have this
- Project backup to Mac (copy project + audio pool) — core value proposition; trivially expected
- Backup verification with checksums — differentiates from Finder copy; builds trust
- Project duplicate/copy with path remapping — prerequisite for safe experimentation
- Automatic snapshot before every write — non-negotiable; the safety model cannot be partial

**Should have (differentiators — v1.x after validation):**
- Snapshot history browser and rollback — unique; activate once snapshot storage is proven
- Dry-run preview for destructive operations — unique; no competitor shows what will change before committing
- Atomic staged writes (all-or-nothing) — unique; the root-cause fix for documented data loss incidents
- Audio file format validation (44.1kHz, 16/24-bit WAV/AIFF) — low effort, prevents silent OT load failures
- Unused sample detection (assigned but untriggered) — cross-reference query on existing parsed data
- Export project with collected samples (self-contained zip) — OctaZip equivalent; fills documented gap
- Project search and filtering via SQLite index — quality-of-life once many projects are indexed
- Cross-project bank copy with sample remap — highly requested; requires write-path maturity

**Defer (v2+ — requires all write-path pieces proven):**
- Sample assignment from desktop drag-and-drop to slot — highest value but touches all write-path systems; build last
- Wallflower library integration — high-value differentiator; must not block launch; requires stable core
- Sample audio preview — needs audio engine; use system Quick Look as bridge until then
- Pattern/sequencer editing — separate product scope; binary format complexity dwarfs management scope; do not tackle
- Windows support — evaluate demand post-launch

### Architecture Approach

The architecture follows a strict layered model: React/Next.js frontend communicates exclusively through Tauri IPC to a Command Layer of thin entry points, which delegate to Domain Services that have no Tauri dependency. The OT Parser is isolated as a pure Rust module (`domain/ot_parser/`) with no I/O capability — it produces `TransactionPlan` values (Vec of `FileWrite { path, bytes }`) rather than writing files directly. The Atomic Write Engine consumes these plans: stage to temp dir on the same volume, validate by re-parsing each staged file, then atomically rename all files into place. The Snapshot Store uses content-addressed blob storage (SHA-256 keyed) with a SQLite manifest, giving automatic deduplication across snapshots. All runtime state lives in `Mutex<AppState>` registered via Tauri's `manage()`. Long operations emit progress events via `app_handle.emit()` to keep the UI responsive.

**Major components:**
1. OT Parser (`domain/ot_parser/`) — pure Rust, no Tauri, no I/O; produces `TransactionPlan`; must be built and validated first
2. Atomic Write Engine (`domain/atomic_write.rs`) — stage-validate-rename; enforces same-filesystem staging; calls `fsync`
3. Transaction Coordinator (`domain/transaction.rs`) — orchestrates: pre-snapshot then plan generation then write engine; wires safety layers
4. Backup Service + Snapshot Store — pre-write snapshot, content-addressed blob storage, revert via same write engine path
5. Takoyaki SQLite DB (`db/`) — project index, snapshot manifest, sample assignments; `rusqlite_migration` for schema
6. Volume Detector (`services/volume_detector.rs`) — DiskArbitration for mount/unmount; Kqueue for file changes; emits Tauri events
7. Wallflower Service (`services/wallflower.rs`) — read-only pool; gracefully disabled if DB absent or locked
8. Command Layer (`commands/`) — thin Tauri entry points; validate inputs, call domain services, serialize results
9. React Frontend — TanStack Query for command results; Zustand for UI state; mocks during early development

### Critical Pitfalls

1. **One/zero index mismatch corrupts slot references** — Project file uses one-indexed slot IDs; all other files (bank, markers, sample settings) use zero-indexed. Define `ProjectSlotId(u8)` and `SlotRef(u8)` newtypes with explicit conversion; never use raw `u8` for slot IDs. Validate with round-trip slot-move integration tests across all file types.

2. **Unknown/reserved bytes get zeroed on write** — 31.6% of the OT format is undocumented. Every struct must carry opaque `[u8; N]` fields for all unknown regions, preserved verbatim on write. Enforce `parse(serialize(parse(bytes))) == parse(bytes)` as an automated test against a corpus of real project files before any write path ships.

3. **Multi-file operations written sequentially without a changeset model** — A single slot assignment touches up to 18 files; partial writes leave projects unrecoverable on hardware. The changeset (`TransactionPlan`) model must exist before the first write of any kind. Never write any OT file outside the stage-validate-rename transaction.

4. **USB hot-unplug loses data because fsync is skipped** — macOS buffers FAT32 writes. Report success only after `fsync` on every written file plus parent directory sync. Expose a prominent "Safely eject" button; never dismiss the write progress indicator until fsync is confirmed.

5. **GPL contamination from ot-tools-io** — ot-tools-io is GPL v3; Takoyaki is MIT. A clean-room specification document (no code, derived from community sources only) must exist before any parser code is written. Never add ot-tools-io to any Cargo.toml, even dev-only.

## Implications for Roadmap

Based on all four research files, the natural phase structure follows the component build order from ARCHITECTURE.md, shaped by pitfall phase assignments from PITFALLS.md and the feature dependency graph from FEATURES.md.

### Phase 1: Foundation — Parser, Safety Model, and Volume Integration

**Rationale:** The OT binary parser is a prerequisite for every other feature. All write-path pitfalls (index mismatch, unknown bytes, partial writes, fsync, GPL contamination) must be resolved before a single byte is written to the CF card. The safety model (snapshot + atomic write) must be in place before any mutating operation is exposed. Volume detection is the entry point for all user workflows.
**Delivers:** Verified read/write parser for all OT file types; atomic write engine; pre-write snapshot infrastructure; USB volume detection; project listing and bank visualization (first visible UI)
**Addresses:** USB mount detection, project listing, bank visualization, sample slot listing, project backup to Mac, automatic snapshot before write (P1 features)
**Avoids:** Index mismatch (newtypes from day one), unknown byte zeroing (round-trip tests as merge gate), partial writes (changeset model before first write), fsync omission, GPL contamination (spec document before code)
**Research flag:** Needs `/gsd-research-phase` — OT binary format is partially undocumented; clean-room spec document creation is itself a research task before coding begins

### Phase 2: Read-Only Feature Set

**Rationale:** With the parser proven, ship all read-only features as a safe, high-value milestone. Validates the parser against real-world project diversity without write risk, and delivers immediate value to users (browsing, slot visibility, missing sample detection).
**Delivers:** Full project metadata display; bank/pattern visualization; Flex + Static sample slot listing (128 each); missing sample detection; audio format validation; project search and filtering via SQLite index
**Addresses:** Bank visualization, sample slot listing, missing sample detection, audio format validation, project search/filtering (P1/P2 features)
**Avoids:** Writing before the parser is field-validated; exposes no write commands before safety model is proven
**Research flag:** Standard patterns — no deep research needed; builds directly on Phase 1 parser output

### Phase 3: Write Operations and Backup

**Rationale:** With the parser proven on real files and the atomic write engine tested, activate the write path starting with the lowest-risk operations (backup/duplicate) and progressing to the full three-layer model.
**Delivers:** Project backup to Mac with checksum verification; project duplicate/copy with path remapping; dry-run preview for all destructive operations; atomic staged writes; snapshot history browser and rollback
**Addresses:** Project backup, backup verification, project duplicate/copy, dry-run preview, atomic staged writes, snapshot history + rollback (P1/P2 features)
**Avoids:** Writing without snapshot (snapshot created in Phase 1 is now activated); partial writes (changeset model from Phase 1 enforced here); hot-unplug loss (fsync in atomic write engine)
**Research flag:** Standard patterns for backup/copy; snapshot deduplication (content-addressed SHA-256) is well-documented

### Phase 4: Advanced Management Features

**Rationale:** With the write path and safety model proven, add high-complexity management features that depend on the full stack being stable.
**Delivers:** Export project with collected samples (zip archive); unused sample detection; cross-project bank copy with sample remap; project rename with binary header update
**Addresses:** Export with collected samples, unused sample detection, cross-project bank copy (P2 features)
**Avoids:** Cross-project write operations before atomic write engine is field-proven; bank copy before slot-remap logic is validated
**Research flag:** Cross-project bank copy slot conflict resolution may benefit from `/gsd-research-phase` — it is the most complex write operation and no active tool has an open-source reference implementation

### Phase 5: Sample Assignment and Wallflower Integration

**Rationale:** The hardest write operation (sample assignment from desktop to slot) and the optional Wallflower integration are deferred until the entire write path is proven and mature. Wallflower must degrade gracefully when absent.
**Delivers:** Sample assignment from desktop (drag-and-drop to Flex/Static slot with path handling and .ot sidecar management); Wallflower library integration (read-only SQLite query, metadata-rich sample browser, graceful degradation)
**Addresses:** Sample assignment from desktop, Wallflower integration (P3 features)
**Avoids:** Sample assignment before all 18-file coordination is proven in Phase 3/4; Wallflower DB locking crashing the app (busy_timeout, graceful degradation contract defined at feature boundary)
**Research flag:** Needs `/gsd-research-phase` for Wallflower DB concurrency handling and WAL mode detection

### Phase Ordering Rationale

- Parser-first ordering is non-negotiable: every write feature depends on a correct, field-validated parser. Shipping write operations before the parser is proven against real OT hardware is the primary risk vector.
- Read-only features (Phase 2) before write features (Phase 3+) serves dual purpose: delivers user value early and stress-tests the parser against diverse real-world project files without write risk.
- The three-layer safety model (snapshot, dry-run, atomic write) must be complete before any write-path feature ships — the FEATURES.md dependency graph makes snapshot a prerequisite for every destructive operation.
- Wallflower integration and sample assignment are last because they depend on every other system being stable, and their complexity (SQLite concurrency, 18-file coordination) is highest. Delaying them does not reduce launch value.
- The clean-room GPL boundary must be enforced from the beginning of Phase 1, not addressed retroactively.

### Research Flags

Phases likely needing deeper research during planning:
- **Phase 1:** OT binary format spec document creation — the format is 31.6% undocumented; community reverse-engineering sources need to be assembled into an independent spec before coding. Also: macOS DiskArbitration FFI for volume detection has sparse documentation.
- **Phase 4:** Cross-project bank copy — slot conflict resolution (auto-merge vs user-directed) has complex edge cases and no open-source reference implementation.
- **Phase 5:** Wallflower DB concurrency — WAL mode detection, busy_timeout configuration, and the graceful-degradation contract need explicit API research before implementation.

Phases with standard patterns (skip research-phase):
- **Phase 2:** All read-only features build directly on the Phase 1 parser; no novel patterns.
- **Phase 3:** Backup/copy/snapshot follow documented content-addressed storage patterns; atomic write via temp-file-rename is well-documented.

### Gaps to Address

- **OT format completeness:** 31.6% of the binary format is undocumented. The parser spec document is a research deliverable in Phase 1, not a precondition for planning. Budget time for hex analysis of real project files from multiple OT firmware versions.
- **Firmware version range:** Research confirmed OS version field causes hard load failures but does not enumerate which firmware versions are in active use in the community. Field testing with real OT hardware is required in Phase 1.
- **macOS DiskArbitration FFI:** Confirmed as the correct approach for volume mount detection; the specific Rust FFI binding was not fully resolved. The `sysinfo` crate + `notify` Kqueue backend may be sufficient as an alternative; validate early in Phase 1.
- **CF card FAT32 atomicity:** Atomic rename on FAT32 via macOS is assumed to follow POSIX semantics. Verify with an integration test on an actual FAT32 volume before depending on it in Phase 3.
- **Snapshot storage location:** Architecture suggests `~/.takoyaki/snapshots/` for long-term history but staging for atomic writes must be on the CF card volume. The dual-location pattern needs explicit design at the Phase 1/3 boundary.
